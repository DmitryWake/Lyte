# Схема БД в Lyte

Room KMP в `:core:core-db`. У пользователя в этой БД лежит вся история тренировок — потерять её
нельзя ни при каком обновлении. Отсюда все правила ниже.

## Комплект из четырёх частей

Меняешь схему — **в том же коммите** обязаны появиться все четыре. Три из четырёх — это не «сделано»,
это сломанное обновление у пользователя.

1. Бамп `version` в `@Database`.
2. Объект `Migration` в `db/migration/` и его регистрация в `LYTE_MIGRATIONS`
   (`RoomBuilderDefaults.kt`).
3. Новый файл схемы в `core/core-db/schemas/` — он экспортируется KSP и **коммитится в гит**.
4. Тест миграции. Эталон — `Migration1To2Test`.

`fallbackToDestructiveMigration` запрещён: он стирает историю при любом бампе версии.

## Как пишется тест миграции

Смотри `core/core-db/src/androidHostTest/.../migration/Migration1To2Test.kt`. Принцип: БД **предыдущей**
версии собирается по DDL из уже закоммиченной схемы (`schemas/…/N.json`, поле `createSql`),
наполняется данными, мигрируется настоящей `Migration`, затем проверяются данные.

- DDL в тесте дублируется намеренно: тест обязан описывать состояние «до» независимо от текущих
  `@Entity`, иначе он проверяет миграцию против уже изменённой схемы и всегда зелёный.
- Тест живёт в `androidHostTest`, не в `commonTest`, и берёт `AndroidSQLiteDriver` под Robolectric:
  приложение работает на `BundledSQLiteDriver`, но его JNI собран под Android и на host-JVM падает
  с `UnsatisfiedLinkError`. SQL от драйвера не зависит, поэтому проверка на Android покрывает и iOS.
- Проверяй не только «колонка появилась», но и что старые строки получили осмысленные значения
  (дефолты, бэкфилл), а не `NULL`.

## Внешние ключи и каскады

`ON DELETE CASCADE` в SQLite срабатывает **только** при `PRAGMA foreign_keys = ON`. Room ставит её в
сгенерированном `onOpen`, поэтому в приложении каскад работает — но если пишешь тест на удаление,
собирай БД через настоящий Room-билдер, а не сырым драйвером: иначе прагмы не будет и тест докажет
не то.

Текущие каскады: `session_exercise.session_id → workout_session` и
`session_set.session_exercise_id → session_exercise`. FK `session_exercise.exercise_id → exercise`
идёт **без** каскада: упражнение, на которое ссылается сессия, удалять нельзя.

## Soft-delete вместо удаления

`workout.is_archived` и `exercise.is_archived`. Правило в `deleteOrArchiveWorkout` /
`deleteOrArchiveExercise`: есть ссылки — архивируем, нет — удаляем, всё одной транзакцией, чтобы
подсчёт и запись были атомарны. История обязана пережить удаление программы.

Известный долг: архивная запись, осиротевшая после удаления последней ссылавшейся сессии, остаётся
в БД. Чистки нет.

## Стоимость запросов

Список истории читается **двумя** запросами: строки сессий и подходы всех завершённых сессий разом
(`getFinishedSessions` + `getFinishedSessionSets`), затем раскладывается по id в репозитории. Не
дотягивай граф на каждую карточку — это N+1.

Бизнес-правила в SQL не переезжают: исход подхода считает доменная `SessionSetOutcomeUtils.outcome()`,
одна и та же для трека истории и для диффа деталей.

## Мелочи, на которых легко обжечься

- Room не подставляет `const` в `@Query` — строковые литералы вроде `'COMPLETED'` дублируются, и это
  надо покрывать тестом.
- KSP подключается **per-target** (`kspAndroid`, `kspIosArm64`, `kspIosSimulatorArm64`), общего
  `ksp(...)` нет.
- `room { schemaDirectory(...) }` обязателен при `exportSchema = true`, иначе KSP-таска падает.
- Сущности и DAO лежат в `core/core-db/src/commonMain/.../db/<domain>/`; фичи получают их через DI
  (`coreDbModule()`), а не создают БД сами.

Подробности и полный список сущностей — `core/core-db/README.md`. При изменении публичного API
модуля этот README правится в том же коммите.
