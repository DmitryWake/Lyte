# Переход Lyte на дизайн-систему v2 — список задач

Документ описывает полный переход приложения на редизайн (DS v2 + новые экраны).
Каждая задача (`RD-xx`) рассчитана на **отдельную сессию Claude Code**: сессия сама строит план и выполняет его.
Исключение — RD-22, где первая часть делается в Claude Design (готовый бриф внутри задачи).

## Как запускать задачу

Шаблон стартового промпта для новой сессии:

```
Задача RD-07 из roadmap/design-v2/TASKS.md. Прочитай CLAUDE.md, README изменяемых модулей
и указанные в задаче файлы дизайна. Построй план реализации, покажи его, затем выполни.
```

Правила, действующие для **каждой** задачи (не дублируются в описаниях):

- CLAUDE.md — источник правды по кодстайлу, MVI, навигации, модулям.
- Ветка от `development`, один осмысленный коммит, PR; Claude не мержит.
- Перед PR — гейт из CLAUDE.md § «Тесты» (host-тесты + iosSimulatorArm64 + `:androidApp:assembleDebug` + `:shared:linkDebugFrameworkIosSimulatorArm64`).
- Меняешь исходники core-модуля — обнови его `README.md` в том же коммите.
- Хардкод строк в `@Composable` запрещён: всё в `composeResources/values/strings.xml`.
- `@Preview` обязателен для новых/изменённых экранов и публичных компонентов. Превью — **источник истины
  для скриншот-тестов**: каждое автоматически снимается в светлой и тёмной теме. Состояние без превью
  визуально не проверяется, поэтому новые армы `UiState` (пустой список, ошибка, «много подходов»)
  добавляются превью осознанно.
- **Эталоны скриншотов руками не коммитим** — их перегенерирует и кладёт в ветку PR джоба `screenshots`
  (см. CLAUDE.md § «Скриншот-тесты»). Пушим только код; в diff'е PR видно before/after каждого экрана —
  для редизайна это основной способ ревью визуала.
- Новый модуль с `@Preview` подключает convention-плагин `id("lyte.screenshot")` и объявляет один
  параметризованный тест-класс (~10 строк, эталон — `feature/workout/impl`).
- К концу задачи проект компилируется и не содержит «двух параллельных реализаций» одного и того же.

  Ещё (найдено тестировщиком RD-19): **у подарма `NoActiveSession(picker = …)` нет экранного кадра** —
  единственный оверлей проекта, который можно снять на уровне экрана (шторка stateless, Koin не нужен,

  свидетеля не имеет. Не взято в RD-19: потребовало бы расширить видимость чужой file-private фикстуры
  в задаче, которая обещает только добавлять.
  Ещё (найдено реализатором RD-26, уточнено ревью): **упражнение без подходов можно сохранить** —
  валидации на пустой список нет. Оно не даёт строк в плоском запросе истории и выпадает из нумерации

  свёртки `toPreviousSetResults`.
  Ещё: **ландшафт не верстался и не снимался ни одним превью.** Решением 10 ориентация лочится в

## Что проверено и не меняется

Сверено сплошной инвентаризацией кода против бандла. Работы не требует — не переоткрывать:

- **Все 27 компонентов манифеста `_ds_bundle.js` реализованы.** Пробелов манифест → код нет. Сверх
  манифеста в ките `LyteSetEditRow`, `LyteStepperRow`, `LyteWordmark`, `LyteDiffDelta` — осознанные
  добавления, часть из них признаёт `<DS>/readme.md` § Caveats.
- **Токены перенесены полностью**, кроме hit-target (см. RD-21). `--ref-*` (референсный слой M3) и
  `--shape-none` не переносятся осознанно: первое в Compose не нужно, второе — это `RectangleShape`.
- **Палитра M3, типографика, spacing-сетка, shape-шкала, шрифты, вордмарк** — не менялись в v2.
- **Пиктограммы движений и акценты совпадают 1:1** — 10 ключей и порядок сетки, 6 акцентов и
  порядок, дефолты `squat` и `slate`.
- **Герой-иконки пустых состояний совпадают** на всех пяти экранах, где они есть.
- **Склонения корректны.** Более того, в одном месте код **правильнее** бандла — см. решение 7.
- **Около сорока строк совпадают дословно** с кадрами: пустые состояния, диалоги удаления,
  плейсхолдеры форм, лейблы кнопок.
- **Схема БД под все кадры достаточна.** Единственное отсутствующее — не колонка, а запрос
  (RD-26). Схема бампится в этом эпике ровно один раз, под флаг обучения (RD-28).
- **28 из 33 кадров канваса реализованы.** Не реализована одна группа — обучение 0.0–0.4.
- **Восстановление активной сессии после убийства процесса работает** — сделано лучше, чем в
  прототипе, терять нельзя.
- **Вложенный стек шторок редактора не теряется:** возврат из «Нового упражнения» ведёт в выбор с
  сохранённым запросом — эквивалент `pop` в прототипе.
- **Мёртвое в самом бандле, не пропуск реализации:** шторка `shMenu` («Редактировать / Удалить
  программу») не открывается ни одним пресетом, в `programRows` написано «кебаб с меню убран»;
  функция `short()` объявлена и не вызывается. В коде их правильно нет.

## Принятые решения

Закрыты один раз на весь эпик. Задача, которая с ними спорит, спорит с роадмапом.

1. **Формат пиктограмм упражнений — PNG + тонирование** (решено). В бандле 512×512 PNG (чёрная линия на
   прозрачном); в Compose эквивалент CSS-маски — `Image(..., colorFilter = ColorFilter.tint(...))` по альфе.
   Трассировка в вектор ухудшит рисунок, поэтому правило CLAUDE.md «иконки — vector drawable `ic_*.xml`»
   дополняется исключением для пиктограмм движений (внесено в RD-03).
2. **Атрибуция Flaticon.** Бесплатная лицензия требует кредит, «понятный, видимый и легко находимый для
   аудитории»; для приложений — в разделе credits/acknowledgements. Страницы на GitHub Pages
   **достаточно как места хранения текста, но не как единственного решения**: на неё должна вести
   видимая ссылка из приложения. Итог: `docs/LICENSES.md` на Pages + точка входа в приложении —
   экран «О приложении» (RD-22).
   **Нетехническая альтернатива, снимающая требование целиком:** месяц Flaticon Premium — иконки,
   скачанные при активной подписке, разрешено использовать без атрибуции (сохранить сертификаты).
   Тогда RD-22 из блокера выпуска превращается в обычную задачу (он всё равно несёт OFL и версию).
   Решение за владельцем; пока не принято — RD-22 блокер.
3. **3.3/3.4 остаются шторками, но получают хром макета** (решено). В кадрах это полноэкранные
   push-экраны; переход на роуты требует канала результата в `:core:core-navigation` — а
   `LyteNavigator` односторонний, `NavController` за пределы `App()` не выходит, значит
   `SavedStateHandle` предыдущего entry недоступен. Это самая необратимая позиция эпика: публичный
   API core-модуля, у которого через полгода будут другие потребители. Плюс редактор подходов вообще
   ничего не возвращает — он правит чужой черновик, и единственный владелец черновика при выносе в
   роут растворяется. Со стороны пользователя цена расхождения близка к нулю: программы собирают
   дома, а не в зале. Берём дешёвые 80% фидельности — заголовок и affordance «назад» у шторки.
   Отклонение зафиксировано в `core-design/README.md`.
4. **`ExerciseAccent`/`ExerciseGlyph`: два enum'а.** Доменные — в `:core:core-workout`, UI-шные
   (`LyteAccent`/`LyteExerciseGlyph`) — в `:core:core-design`; фича мапит домен → UI в своём `UiMapper`.
   `core-design` не должен знать про домен, `core-workout` — про Compose.
5. **Источник правды по тону — кадры канваса, `readme.md` — комментарий.** `readme.md` объявляет
   v2-тон («С чего начнём?», «Готово. Отдыхай», компактная нотация), которого нет ни в одном кадре, а
   код уже в двух случаях из трёх следует кадрам. Кадры выигрывают ещё и потому, что по ним снимаются
   скриншоты. Расхождение readme ↔ кадр находкой не считается.
6. **Формат значения подхода выбирается по месту вызова, а не одной общей функцией.** Ориентиры
   («Цель», «В прошлый раз») получают развёрнутый вид «10 повт × 62,5 кг» как в кадрах; спокойные
   строки списка и пилюли в шторке остаются компактными — весь смысл спокойной строки в том, что семь
   их помещаются рядом с фокус-карточкой, а многословный вариант распирает 36dp-строку.
7. **Плюрал «N из M подходов выполнено» остаётся как есть.** Бандловский `cnt()` даёт именительное
   согласование («1 из 1 подход выполнено»), код — родительное после «из», то есть грамматически
   правильно. Дословный перенос внёс бы ошибку. Единственное место, где код осознанно расходится с
   кадром.
8. **Коуч-марки 0.1–0.4 рисуются на репликах, а не поверх реальных экранов.** Прототип фабрикует
   сессию (`goToStep`) и сеет историю; на реальном первом запуске нет ни того, ни другого. Отвергнуты:
   *демо-сессия в боевых таблицах* — нарушает SSOT, ломает инвариант «активная сессия одна», при
   убийстве процесса посреди тура гейт лендинга угонит пользователя в тренировку, которую он не
   начинал, а её завершение перепишет цели засеянной программы фейковыми фактами; *контракт якорей
   поверх реальных экранов* — сквозная граница в трёх фича-модулях, ломается молча при рефакторинге
   чужого экрана, и главного вопроса «что показать под скримом» не решает; *вызов чужих `*Content`* —
   единственное ребро `impl → impl` в графе. Реплики: модуль самодостаточен, замер координат не нужен
   вовсе, откат = удаление модуля. **Побочно решается шаг 0.4:** реплика показывает карточку истории,
   поэтому пустая история новичка перестаёт быть тупиком.
   Цена названа честно: реплика расходится с реальным экраном молча, компилятор и скриншот-гейт этого
   не поймают. Митигация — реплики строго из `Lyte*`-компонентов, лейблы кнопок из тех же строковых
   ресурсов, что на боевых экранах.
9. **Обучение показывается только новым пользователям.** Миграция v2→v3 делает backfill
   `has_completed_onboarding = has_completed_first_launch`. Иначе в день обновления тур вылезет всей
   установленной базе поверх реальных данных и, возможно, поверх активной сессии.
10. **Ориентация лочится в портрет на время эпика.** Манифест не задаёт ни `screenOrientation`, ни
    `configChanges`, при этом ландшафт никогда не верстался и не снимался ни одним превью. Считать его
    поддерживаемым — значит взять в эпик вёрстку 33 кадров в другой ориентации.
11. **«В прошлый раз» прячется, когда совпадает с «Цель».** Завершение сессии подтягивает цель под
    факт каждого **выполненного и сопоставившегося** подхода: упражнение сопоставляется по позиции и
    id из библиотеки, подход — по позиции в пределах числа подходов плана; пропущенные, лишние и
    несопоставившиеся цель не меняют, а если программу правили между сессиями — цели перезаписаны
    заново. Значит по умолчанию `target == last` для большинства подходов, и вторая строка дублирует
    первую. В бандле они разные только потому, что в прототипе прогрессии нет; кадр это не
    доказательство. Строка появляется ровно тогда, когда несёт информацию.
12. **Пропущенный в прошлый раз подход — ищем глубже.** Завершение сессии одной транзакцией
    помечает `SKIPPED` все подходы с пустым результатом, поэтому у досрочно завершённой сессии такие
    подходы есть всегда — и не обязательно в конце: переключатель упражнений позволяет закрыть поздние
    и оставить ранние, так что пропущенные идут вперемешку с выполненными. Отличить их от подходов,
    пропущенных пользователем вручную по ходу сессии, нельзя — статус один. Берём последнюю сессию,
    где подход **реально делали**. Дороже на одно условие в запросе, зато ориентир не пропадает у тех,
    кто чаще завершает досрочно.
13. **Досрочное завершение уводит в детали сессии — через лендинг.** `navigateToSessionDetails()`
    начинается с `navigateToLanding()` (замена `ActiveSessionRoute` на `TrackerLandingRoute` в стеке
    трекера), затем `switchTab(HistoryTabGraph)` и переход на детали. KDoc `OnEndEarlyConfirmed`
    описывает только первый шаг и потому читается как «уходим на лендинг» — он не противоречит коду,
    а недоговаривает. Поведение верное: правило пика и конца — последнее впечатление сессии должно
    быть её результатом. KDoc дописывается в RD-21 вместе с текстами того же диалога.

- **У трека плана есть порог плотности** (`lytePlanTrackWidth`). Слот расширен с 56 до 76dp, сегмент

## RD-07 · Сессионные компоненты: TrackSetRow v2 и ExerciseSetList ✅

**Статус: сделано** (ветка `claude/design-v2-migration-c1sflx`).

**Что сделано.** `LyteTrackSetState` — sealed-модель подхода (`Resting`/`Current`) отдельным файлом;
`LyteTrackSetRow` переписан под неё: пять спокойных тонов (крестика нет ни в одном) и фокус-карточка
с внутренней обводкой 2dp, ориентирами «Цель»/«В прошлый раз» отдельными подписанными строками и
слотом под заметку. `LyteExerciseSetList` — композиция экрана: один скроллер, якорь фокус-карточки,
маска верхнего края, появление выполненной строки. Шесть превью (спокойные состояния, карточка,
списки на 3 и 8 подходов — первый/середина/последний, длинная заметка, пропуск) — CI снимет их в
светлой и тёмной теме.

Решения, которые стоит знать дальше:

- **Тон спокойной строки — существующий `LyteProgressTone`, а не собственный enum строки.** Он уже
  объявлен общим словарём системы («и в треке сводки, и в строке подхода, и в деталях сессии») и
  несёт ровно те же пять исходов. Третий параллельный словарь пришлось бы сводить в RD-08; вместо
  этого сводить остаётся только `LyteDiffTone`.
- **Липкий низ заменён якорем прокрутки.** `position: sticky; bottom: 0` в Compose нет, поэтому
  перенесено поведение: карточка — обычный элемент списка, а её низ доводится до 104dp от низа
  области программной прокруткой. Над первым подходом лежит отбивка в высоту области — без неё
  карточку первого подхода нечем опустить к якорю (в вебе это те же 640px).
- **Первая установка позиции мгновенная, анимируется только смена подхода.** Так же гейтит прототип
  (`_firstLayout`), и это же спасает скриншоты: часы композиции остановлены, анимированная прокрутка
  до кадра не доехала бы и эталон снялся бы на пустой отбивке.
- **Появление выполненной строки анимируется слоем (alpha + `translationY`), а не `AnimatedVisibility`.**
  Размер при этом не меняется, поэтому измеренный низ карточки не пляшет и якорь не дрожит.
- **260 мс прототипа взяты токеном `motion.durationMedium` (250).** Правило «все анимации берут
  значения из токенов» важнее 10 мс; кривая прокрутки — `easingDecelerate` (ease-out cubic ручного
  твина в прототипе).
- **Спокойная строка держит 36dp явным интерлиньяжем** (18sp): со стилевым `lineHeight` из
  типографики строка распухала до 38dp. Высота — минимальная, а не фиксированная, поэтому крупный
  системный шрифт её растянет, а не обрежет.
- Строки-хром: добавлены `set_of_total`, `set_skipped`, `set_reference_target`, `set_reference_last`,
  `set_caption_weight_name`; `set_last_time` удалена (ориентир стал подписанной строкой),
  `set_caption_weight` → `set_caption_weight_unit` — она осталась у `LyteSetEditRow`, где подпись
  это единица «Кг», а не имя параметра. Из списка строк RD-09 в фиче остаются только экранные
  («Последний подход», «Последний подход в упражнении») — остальные приехали сюда как хром компонента.

`LyteSetOverview` намеренно не тронут: он удаляется в RD-09 вместе с последним потребителем.

**Цель.** Собрать в ДС новую механику экрана трекинга.

**Источник.** `_ds_bundle.js`: TrackSetRow 2320–2541 (в т.ч. комментарий с обоснованием), ExerciseSetList

**Объём.**

    `Miss` → `diffNegative`/`diffNegativeBg`/`CircleArrowDown`; `Skip` → `diffSkipped`/`diffSkippedBg`/

- Относительная дата: «Сегодня» / «Вчера» / «N дней назад» до недели, дальше обычная дата. Считает

- Пустое состояние — текст макета.

**Оговорка.** «2 дня назад» в скриншотах рендерится как «2 дней назад»: среда рендера не русская,
plural падает в форму `other`. Известно с RD-06, на устройстве форма правильная.

## RD-20 · Формат чисел: запятая, неразрывный пробел, единый форматтер

**Источник.** `LyteScreen.dc.html:526–536` — `num(v) = String(v).replace(".", ",")`, NBSP между
числом и единицей и внутри `cnt()`. `<DS>/readme.md` § Content fundamentals: «decimals use a comma».

**Что не так сейчас.** `formatWeight` возвращает `weight.toString()` → «62.5», и его KDoc это
закрепляет («дробный — как есть»). Литерального NBSP нет ни в одном файле репозитория.

**Ловушка задачи: форматтеров два, и они уже расходятся.** Кроме публичного `formatWeight`
(`WeightFormat.kt:7-10`) есть приватный `formatStepperValue` (`LyteStepper.kt:255-261`), который
сначала округляет до двух знаков — на `62.4999` первый даст «62.4999», второй «62.5». Обе функции
**сосуществуют в одном компоненте** `LyteTrackSetRow` (`:192/:327/:330` против `:283/:296`).
Поправить только `formatWeight` — получить «Цель 8 повт × 62,5 кг» над степпером, показывающим
«62.5». Внутри самого степпера функция одна на три вызова, поэтому отображение и драфт ручного ввода
между собой не разойдутся — расходятся именно два форматтера.

**Объём.**
- Один формат на оба места: `formatWeight` и степпер.
- NBSP между числом и единицей и в счётчиках — **только на выводе**.
- Развести формат по месту вызова согласно решению 6. Задеты `LyteTrackSetRow` (спокойные строки и
  обе строки-ориентира), `LyteDiffRow` (детали истории), `ExerciseInfoSheet`, `ActiveSessionOverlays`
  (пилюли целей) — то есть трекер, история и редактор программ разом.
- Ввод не сужать: регулярка степпера принимает `[.,]`, `commit()` нормализует — так и оставить,
  клавиатура даёт разделитель по системной локали.
- Нормализовать NBSP → обычный пробел в `name_normalized` и в поисковом запросе. Поиск матчит
  `name_normalized LIKE`, а `name_normalized` — это `name.lowercase()` без приведения пробельных
  символов; NBSP внутри имени (их вставляют iOS-клавиатуры) сломает **тот запрос, который эту позицию
  перекрывает** — упражнение при этом остаётся доступно пустым запросом, другой подстрокой и по id.
  Деградация поиска, а не потеря упражнения.

**Зависимости.** RD-19.

**Затрагивает.** `core/core-design/.../format/WeightFormat.kt`, `.../format/SetValueFormat.kt`,
`.../component/stepper/LyteStepper.kt`, `.../component/session/LyteTrackSetRow.kt`,
`.../component/feedback/LyteDiffRow.kt`; `core/core-workout/.../data/mapper/`,
`core/core-db/.../workout/ExerciseDao.kt`; эталоны всех четырёх фич. README `core-design`.

**Приёмка.** Юнит-тесты **на форматированную строку**, которых сейчас нет ни одного: `formatWeight`
даёт «62,5» и «60»; метка значения подхода в обоих режимах; NBSP присутствует в выводе и отсутствует
в `name_normalized`. Тест: упражнение с NBSP в имени находится по запросу с обычным пробелом. Ни на

один разделитель и одно округление — видно на превью; тест на `62.4999` даёт одинаковый результат

## RD-23 · Архивная программа не запускается и не воскресает

**Источник.** Сверка кода. Два дефекта в смерженном коде:
- `WorkoutDao.getItems()`/`observeItems()` фильтруют `is_archived = 0`, а `getWithExercises(id)` —
  нет, поэтому `WorkoutRepository.getWorkout(id)` возвращает архивную программу;
- `WorkoutEntity.toRows()` строит `WorkoutDatabaseEntity` без `isArchived` → дефолт `false`, а
  `saveWorkoutGraph` делает `upsertWorkout` → сохранение перетирает флаг архива нулём, и то же
  касается упражнений программы.

Воспроизведение: открыть превью программы во вкладке «Трекер» → удалить её во вкладке «Программы» →
вернуться на трекер → «Начать». Тренировка стартует по удалённой программе. Открыть её в редакторе и
сохранить — программа возвращается в список.

**Объём.** Путь получения программы по id не отдаёт архивные; вызывающие показывают понятное
состояние, а не пустой экран. Путь сохранения перестаёт трогать `is_archived` — ни у программы, ни у
её упражнений. Выбранный способ описать в KDoc: рядом уже есть комментарий, объясняющий, почему

## RD-24 · Асинхронные операции: guard'ы, индикация, невидимые ошибки

**Источник.** Сверка кода. Три дефекта на одном механизме — необработанное состояние «операция идёт».

- **Двойной тап по «Удалить» в деталях сессии может выкинуть за пределы Истории.** У обработчика
  `OnDeleteConfirmed` нет guard'а ни в одном виде — ни джоба, ни флага в `UiState`, ни блокировки
  кнопки в `LyteDialog`. Повторный интент, поданный до того как Compose уберёт диалог (окно — кадр
  рекомпозиции, растягивается при джанке), запускает вторую корутину; повторный `DELETE` идемпотентен
  и тоже даёт успех, так что в канал может уйти второй `back`, а он снимет `HistoryRoute` —
  стартовый destination вкладки — схлопнув `HistoryTabGraph` и `BottomNavGraph`. Исход не
  детерминирован: первый `back` уничтожает entry деталей и отменяет `viewModelScope`, поэтому вторая
  корутина может до `back()` и не дойти. Повтор: История → сессия → «Удалить» → дважды быстро
  «Удалить».
- **`isMutating` на активной сессии не читается нигде.** `mutate()` при занятости молча выходит, но
  кнопки не гасятся и индикатора нет. Хуже всего `saveNote()`: он закрывает шторку **до** вызова
  `mutate`, поэтому проглоченная запись уносит набранную заметку без ошибки и без следа.
- **Ошибка сохранения на экране-итоге невидима.** `finishSession()` сообщает об ошибке через
  `updateTracking`, а тот вне арма `Tracking` — no-op. У `AllDone` поля ошибки нет, баннер живёт
  только в ветке `Tracking`. Кнопка при этом не блокируется (`isMutating` сбрасывается до вызова
  `updateTracking` и всё равно не читается UI) — тап просто выглядит мёртвым, хотя повторный реально
  запустит сохранение снова. В макете состояния ошибки на этом экране нет, поэтому решать надо
  осознанно: арм ошибки для `AllDone` либо общий баннер поверх контента.

- **Баннер неудачного удаления программы невидим.** В `WorkoutListContent` он композится **до**
  `WorkoutProgramList` внутри одного `Box`, а в Compose последующие дети рисуются поверх: первая
  непрозрачная `LyteProgramCard` накрывает его целиком. При неудачном удалении пользователь не
  получает никакого сигнала. Найдено кадром RD-19 — новый кадр `actionError` совпал с базовым
  побайтово, то есть арм под визуальный контроль не попал. Кадр оставлен канарейкой: почините
  порядок композиции — эталон изменится, и это будет видно в диффе.
- **Баннер неудачного старта тренировки нечитаем.** `Text` без подложки в одном `Box` с
  `LazyColumn`, ложится поверх названия первого упражнения; нечитаемы обе строки. Тоже найдено
  кадром RD-19 и тоже зафиксировано в KDoc кадра.

Пункты со второго по пятый — прямое нарушение правила CLAUDE.md «любая длительная операция
отображает loading / content / error».

**Объём.** Guard той же формы, что уже применён в `WorkoutPreviewViewModel.isStarting`, на удаление
сессии. Рисовать `isMutating`. Шторку заметки закрывать только после того, как запись принята. Дать
экрану-итогу способ показать ошибку сохранения. Починить порядок композиции обоих баннеров и дать
им подложку; после этого поправить KDoc двух кадров RD-19, которые сейчас описывают дефект как
намеренно зафиксированный.

**Зависимости.** RD-19.

**Затрагивает.** `feature/history/impl/.../viewmodel/HistorySessionDetailsViewModel.kt`;
`feature/tracker/impl/.../viewmodel/ActiveSessionViewModel.kt`, `.../mvi/ActiveSessionContract.kt`,

**Приёмка.** На чистой установке первым после сплэша идёт приветствие; на установке с данными — не
идёт. «Пропустить» уводит на лендинг, и путь до первого записанного подхода не удлиняется ни на один
тап. После выхода любым способом тур не возвращается, в том числе после убийства процесса. Двойной
тап по «Пропустить» даёт одну команду навигации. После тура в БД нет ни сессий, ни записей истории,
которых пользователь не делал. Превью на каждый арм.

## RD-31 · Обучение: шаги 0.1–0.4 на репликах

**Источник.** Кадры 0.1–0.4; тексты `COACH`, `LyteScreen.dc.html:633–638`.

**Объём.** Четыре статичные нерабочие реплики из компонентов ДС: лендинг с кнопкой «Начать» (0.1),
карточка подхода со степперами (0.2), она же с «Готово»/«Пропустить» (0.3), карточка истории (0.4).
Тапы внутри скрима не обрабатываются, активны только «Далее», «Пропустить» и точки — как в прототипе.
Лейблы кнопок в репликах берутся из тех же строковых ресурсов, что на боевых экранах; где ресурс
недоступен — явная ссылка в KDoc на экран, который реплика изображает.

**Зависимости.** RD-30, RD-29. Плюс RD-27: вторая строка ориентира меняет вид карточки подхода,
которую изображают реплики 0.2 и 0.3 — иначе реплика разойдётся с боевым экраном в день выпуска.

**Затрагивает.** `feature/onboarding/impl` целиком. Другие модули не трогает — это главный аргумент
за реплики.

**Приёмка.** Четыре шага проходятся вперёд и назад, с любого есть выход. Ни один шаг не показывает
пустоту. Пересоздание Activity не сбрасывает шаг и не смещает вырез. Тап по нижнему доку во время
тура ничего не делает. Превью на каждый шаг. Реплика карточки подхода визуально совпадает с боевой —
сверяется глазами по двум кадрам в одном диффе PR.
